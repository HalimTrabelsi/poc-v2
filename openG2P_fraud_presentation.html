01 · Contexte

Pourquoi ce projet existe

OpenG2P est une plateforme open source déployée par les gouvernements pour distribuer des aides sociales à des millions de bénéficiaires. Sans contrôle, cette infrastructure devient une cible facile pour la fraude organisée.

Mamadou crée 5 identités fictives et les inscrit toutes au programme d'aide sociale. Il leur donne le même numéro de téléphone (+224 621 234 567) et le même compte bancaire (#1000). Chaque mois, 5 paiements arrivent sur son seul compte. Sans détection automatique, personne ne le sait.

→ Le problème que ce système résout

Sans notre système

  • 100 % des paiements approuvés sans vérification
  • 15–20 % des bénéfices perdus en fraude
  • Réseaux organisés invisibles
  • Enquête manuelle: 2h par cas
  • Aucune explication pour les agents

Avec notre système

  • 97 % des fraudes détectées automatiquement
  • 5–10 % du budget sauvegardé
  • Réseaux de fraude visualisés en graphe
  • Enquête assistée par IA: 10 minutes
  • Explication en français générée par LLM
02 · Architecture

Les 6 couches du système

Cliquez sur chaque couche pour voir les détails techniques.

01
OpenG2P

Couche d'enregistrement

Base de données des bénéficiaires: nom, téléphone, compte bancaire, date de naissance.

Les données bénéficiaires sont stockées dans PostgreSQL via Odoo. Les tables clés sont:

res.partner g2p_phone_number res_partner_bank g2p_program_membership

Amélioration apportée: auto-finalization — phones + comptes créés automatiquement sans étape manuelle.

02
SQL

Extraction de signaux

Requêtes SQL complexes pour détecter ressources partagées: téléphones, comptes, identités.

Un job tourne chaque minute et pose la question: "Qui partage quoi?"

shared_accounts_count shared_phones_count identity_cluster_count payment_gap_ratio

Les résultats sont stockés dans un Feature Store séparé pour des performances optimales.

03
NetworkX

Analyse réseau

Chaque personne est un nœud. Chaque ressource partagée est une arête. Le graphe révèle les gangs.

La fraude est organisée, pas isolée. Le graphe détecte les bandes:

Détection de cliques Centralité (leaders) network_risk_score
04
XGBoost

Scoring Machine Learning

XGBoost prédit la probabilité de fraude (0.0 à 1.0) à partir de tous les signaux.

XGBoost reçoit toutes les features extraites et renvoie un score de risque:

network_risk=0.95 shared_accounts=3 identity_cluster=2

→ score_final = 0.87 (87% de probabilité de fraude)

Pourquoi XGBoost ? Rapide (<1s), interprétable, excellent avec données déséquilibrées.

05
YAML

Moteur de règles

Règles explicites en YAML: NF001, NF003, IDC001. Chaque règle a un poids et un niveau de risque.

Les règles expliquent pourquoi quelqu'un est flagué. Modifiables sans programmer:

- id: NF001
  name: "Compte bancaire partagé"
  condition: "shared_accounts >= 2"
  weight: 0.35
  risk_level: HIGH

- id: NF003
  name: "Téléphone + Compte partagés"
  condition: "shared_phones >= 1 AND shared_accounts >= 1"
  weight: 0.40
  risk_level: CRITICAL
06
Ollama

Explications IA (LLM)

Quand un cas est CRITICAL/HIGH, un LLM génère une explication en français pour les agents.

Modèle: llama3.2:1b — local, open source, aucune donnée envoyée à l'extérieur.

EXPLICATION GÉNÉRÉE:

"Le bénéficiaire #4887 partage un compte bancaire avec 2 autres personnes et un numéro de téléphone avec 3 autres. Ces signaux combinés constituent un indicateur fort de fraude organisée et nécessitent une enquête immédiate."

03 · Flux de données

De l'inscription au blocage

Chaque étape du parcours d'un bénéficiaire à travers le système.

1

Inscription du bénéficiaire AUTO

L'agent saisit: nom, téléphone, compte bancaire. Le système crée automatiquement tous les enregistrements liés (res.partner, g2p_phone_number, res_partner_bank) sans étape manuelle.

2

Extraction des signaux

Un job toutes les minutes interroge la base: "Combien partagent ce compte? Ce téléphone?" Les résultats alimentent le Feature Store séparé.

3

Analyse réseau (NetworkX) ML

Construction du graphe → détection des connexions → calcul du network_risk_score (0.0–1.0).

4

Scoring ML (XGBoost) ML

Toutes les features → XGBoost → score_final (ex: 0.87 = 87% probabilité de fraude).

5

Évaluation des règles YAML

Le moteur de règles applique NF001, NF003, IDC001… Chaque règle déclenchée ajoute à un score composite → risque_final = CRITIQUE.

6

Explication IA (Ollama)

Le LLM génère automatiquement une explication en français lisible par n'importe quel agent.

7

Création du cas Odoo

Un fraud.case est créé dans Odoo avec: score, niveau de risque, règles déclenchées, explication IA. Alerte temps réel aux agents.

8

Décision humaine

L'agent lit le cas dans le tableau Kanban. Il peut: approuver le blocage, demander plus d'infos, ou rejeter (faux positif).

9

Blocage ou approbation CRITIQUE → BLOQUÉ

CRITICAL → Paiement bloqué jusqu'à approbation. HIGH → Révision manuelle. LOW → Approuvé automatiquement.

07 · Technologies

Pourquoi chaque technologie

🌲

XGBoost

Machine Learning · Scoring

Algorithme d'arbres de décision boostés. Rapide (<1s), interprétable, excellent sur données déséquilibrées. Rejeté: réseau de neurones (trop lent, boîte noire opaque).

🕸

NetworkX

Graph Intelligence · Détection

Bibliothèque Python pour l'analyse de graphes. Détecte les cliques (groupes fermés) et la centralité (leaders de gang). La fraude est collective — un graphe révèle ce qu'un score individuel ne voit pas.

🤖

Ollama (llama3.2:1b)

LLM Local · Explications

LLM open source, 1 milliard de paramètres. Tourne localement: aucune donnée envoyée à l'extérieur. Génère des explications en français compréhensibles par des agents non-techniques.

📋

Règles YAML

Rule Engine · Explicabilité

Fichiers de configuration lisibles par des humains. Les agents métier peuvent ajuster les seuils sans programmer. Complètent le ML avec de l'explicabilité directe.

🐳

Docker

Infrastructure · Isolation

6 services isolés: PostgreSQL, Odoo, fraud-engine (port 8002), Ollama (11434), Prometheus, Grafana. Chaque service tourne indépendamment et peut être mis à l'échelle séparément.

📊

Odoo + Grafana

Interface · Monitoring

Odoo: tableau Kanban pour la gestion des cas (CRITICAL en rouge, HIGH en orange). Grafana: courbes de fraudes détectées par jour, métriques de performance en temps réel.

10 · FAQ Jury

Questions fréquentes

Pourquoi pas 100% de précision?
+
C'est mathématiquement impossible avec des données réelles. Certains cas limites légitimes (compte familial, frères avec même date de naissance) ressemblent à de la fraude. C'est pour cela que la décision finale reste humaine — les agents approuvent ou rejettent chaque cas CRITICAL/HIGH. Un système à 100% de precision signifierait qu'il laisse passer des fraudeurs.
Les données des bénéficiaires restent-elles confidentielles?
+
Oui, intégralement. Tout tourne en local via Docker — aucune donnée n'est envoyée vers un service cloud externe. Le LLM Ollama est aussi local. Si déployé sur serveur gouvernemental, le chiffrement des données peut être activé optionnellement.
Peut-on modifier les règles sans programmeur?
+
Oui. Les règles sont dans des fichiers YAML lisibles. Un agent métier peut ouvrir le fichier, changer "shared_accounts ≥ 2" en "shared_accounts ≥ 3" si le contexte local le justifie, sauvegarder, et le système applique la nouvelle règle. Aucune compétence en programmation nécessaire.
Combien de temps pour former les agents?
+
2 heures de formation suffisent. L'interface Odoo est un tableau Kanban intuitif (rouge = critique, orange = élevé, vert = faible). L'explication IA en français simple fait le reste — les agents n'ont pas besoin de comprendre le Machine Learning pour prendre une bonne décision.
Qu'arrive-t-il si le système se trompe (faux positif)?
+
Le bénéficiaire appelle pour demander pourquoi il n'a pas reçu son argent. L'agent consulte le cas dans Odoo, lit l'explication IA, investigue (appel téléphonique, documents), et peut marquer le cas "DISMISSED" (faux positif confirmé). Le paiement est débloqué immédiatement. Ce processus prend environ 10 minutes. Le taux de faux positifs est de 5–10%, largement acceptable face aux 15–20% de fraude non détectée avant.
Quel est le coût d'infrastructure?
+
Environ $500/mois pour un serveur on-premise ou cloud. À raison de 50–100 cas fraude détectés par jour, avec des montants moyens de plusieurs centaines de dollars chacun, le système se rembourse en quelques jours d'économies réalisées.
