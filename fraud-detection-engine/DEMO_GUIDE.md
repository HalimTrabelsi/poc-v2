# OpenG2P Demo Data & Honest Model Metrics

## 1. Why the First Metrics Were Wrong

| Original (leaked) | Honest (PaySim, leak-free) | Honest (OpenG2P demo) |
|---|---|---|
| ROC-AUC: 0.9998 | ROC-AUC: 1.0000 | **ROC-AUC: 0.9040** |
| PR-AUC: 0.9994 | PR-AUC: 0.9963 | **PR-AUC: 0.8532** |
| F1: 0.9988 | F1: 0.9524 | **F1: 0.8302** |
| Recall: 0.998 | Recall: 0.997 | **Recall: 0.733** |

The original metrics were **target leakage**. PaySim's simulator marks rows as fraud by zeroing `newbalanceOrig` while keeping `amount` non-zero — so any feature derived from `(oldbalance - amount - newbalance)` is literally the label generator. The model was memorising the simulator's rule, not learning fraud.

Even after removing the leak from PaySim, the metrics stay near-perfect because **PaySim is deterministic** — any reasonable model gets perfect scores on it. PaySim is **a poor benchmark for demonstrating production-relevant fraud detection.**

The **OpenG2P demo metrics are the defensible ones** because:

1. The data matches the schema your fraud-engine actually consumes
2. Fraud patterns are realistic (8 distinct archetypes, not one simulator rule)
3. Some patterns are caught well, others poorly — exactly what real-world models do
4. Test set has the same fraud rate as train (no distribution mismatch)

### Audit Columns (Strip Before Import)

The demo CSVs contain two underscore-prefixed columns for evaluation:
- `_fraud_label` — 1 if planted as fraud, 0 if clean
- `_fraud_pattern` — which archetype was injected

**Before importing into OpenG2P, drop these two columns** (Odoo will reject unknown columns or silently ignore them — best to clean first).

## 3. Importing Into OpenG2P Dashboard

### Step 1: Strip audit columns

```powershell
python -c "import pandas as pd; df = pd.read_csv(r'fraud-detection-engine/data/openg2p_demo/openg2p_beneficiaries_import.csv'); df.drop(columns=['_fraud_label','_fraud_pattern','_enrollment_date']).to_csv(r'fraud-detection-engine/data/openg2p_demo/beneficiaries_clean.csv', index=False)"
```

### Step 2: Import via Odoo dashboard

1. Open OpenG2P at http://localhost:8069 (admin / admin)
2. Navigate to **Registry → Individuals**
3. Click **Favorites → Import records**
4. Upload `beneficiaries_clean.csv`
5. Odoo will auto-map columns — verify the mapping looks right
6. Click **Test** then **Import**

### Step 3: Score them through the fraud engine

```powershell
# Single beneficiary
curl -X POST http://localhost:8002/api/v1/score/features `
  -H "X-API-Key: dev-secret-change-in-prod" `
  -H "Content-Type: application/json" `
  -d '{\"beneficiary_id\":\"100001\"}'

# Bulk scoring (all 1000 — recommended for demo)
python fraud-detection-engine/scripts/bulk_score_demo.py
```

### Step 4: Watch in the alert monitor

Open Odoo at http://localhost:8069 and navigate to **Fraud Detection → Live Alert Monitor** — fraud cases will appear in real-time as they're scored. CRITICAL/HIGH alerts push toast notifications via Odoo's `bus.bus`.

## 4. Validating the Model Improvement

Before applying the new model, baseline the current one:

```powershell
# Score all 1000 beneficiaries with the CURRENT model
python fraud-detection-engine/scripts/eval_against_demo.py --before

# Drop in the new model
cp fraud-detection-engine/app/models_saved/xgboost_openg2p_demo.joblib `
   fraud-detection-engine/app/models_saved/xgboost.joblib
docker restart fraud-engine

# Re-score and compare
python fraud-detection-engine/scripts/eval_against_demo.py --after
```

The eval script will produce a side-by-side table:
- recall per fraud pattern
- false-positive count on clean beneficiaries
- average score on fraud vs clean

## 6. What Honest Means

A defensible fraud model should show:

| Property | Why | Our Demo Model |
|---|---|---|
| PR-AUC > random baseline (0.15) | proves the model learned something | 0.85 ✓ |
| PR-AUC < 0.99 | a "perfect" PR-AUC on real data is impossible | 0.85 ✓ |
| Some patterns caught, some missed | real fraud is multi-modal — single model can't catch all | 6/8 patterns caught ✓ |
| Top-k precision degrades with k | recall comes at the cost of precision | 1.0 → 0.45 ✓ |
| Feature importance is distributed | no single feature carries 90%+ | top feat 0.12 ✓ |

If a model violates any of these, suspect leakage.
